KV-Repurpose: A Testbed for Evaluating Non-Prefix KV-Cache Reuse
Taiga Ikeda and Daisuke Miyashita and Jun Deguchi
Kioxia Corporation, Japan
Abstract
KV-cache reuse in large language model serv-
ing is commonly limited to exact prompt pre-
fixes, preventing reuse when the same re-
trieved document appears after different sys-
tem prompts, conversation histories, or dy-
namic metadata. We present KV-Repurpose,
an open-source, vLLM-based system for devel-
oping and evaluating segment-wise KV-cache
reuse beyond exact prefixes. The system com-
bines cache-aware segment scheduling, prompt
construction, capacity management, workload
generation, and runtime monitoring. Experi-
ments on long-context benchmarks show that
naive segment reuse largely preserves out-
put quality for single-document question an-
swering and summarization, while exposing
clear limitations in cross-document reason-
ing. Under a Zipfian RAG-style workload in
which 20% of requests share a fixed prefix,
KV-Repurpose achieves a substantially higher
token-level cache hit rate than prefix caching at
the same 30 GB cache capacity, 63.9% versus
3.3%, resulting in lower TTFT. Even with 1
TB of cache capacity, prefix caching reaches
only a 17.9% hit rate in this workload. Source
code is available under the Apache-2.0 license
at https://github.com/taiga333/
eval-kv-repurpose.

Introduction
Large language models (LLMs) are now widely
deployed in applications such as conversational
assistants, document summarization, retrieval-
augmented generation (RAG), and code genera-
tion. As recent models have become capable of
processing increasingly long inputs, demand for
long-context inference in practical deployments
has grown rapidly. For many LLM serving work-
loads, however, processing long prompts remains
computationally expensive and can substantially
increase time to first token (TTFT) (Gim et al.,
2024).
Figure 1: Motivation.
To avoid repeated prefill computation across re-
quests, modern LLM serving engines employ pre-
fix caching (Kwon et al., 2023; Zheng et al., 2024).
Prefix caching stores the key-value (KV) states
computed for previously processed prefixes and
reuses them when subsequent requests share the
same prefix. It is particularly effective in work-
loads with recurring prefixes, such as multi-turn
conversations (Gao et al., 2024a) and in-context
learning (Brown et al., 2020).
By contrast, in RAG workloads (Lewis et al.,
2021; Gao et al., 2024b), the composition and or-
dering of retrieved documents often vary across
requests. As a result, requests may contain sub-
stantial overlapping content while failing to share
an exact prefix. Widely used serving engines (Liu
et al., 2025), however, primarily optimize exact-
prefix reuse and do not yet support the reuse of the
corresponding KV states in such cases 1, potentially
leading to redundant computation, increased TTFT,
and reduced inference throughput. It can also in-
crease pressure on KV-cache capacity across the
memory and storage hierarchy, including dedicated
context-memory systems (Anschel et al., 2026).

Prior work has explored techniques for pre-

when
cached KV states are reused beyond exact-prefix
matches (Agarwal et al., 2025). Building on this
line of research, we revisit such reuse from a sys-
tems perspective and broadly refer to it as KV-
Repurpose in this paper (Figure 1). Our goal is
neither to claim to be the first to introduce the con-
cept of repurposing nor to propose a state-of-the-
art method for mitigating the accuracy degradation
caused by repurposing. Rather, we seek to reassess
the practical value of KV-Repurpose in large-scale,
long-context inference.
However, simple and reproducible baselines for
integrating non-prefix KV-cache reuse into mod-
ern serving engines remain limited, making it dif-
ficult to assess its practical value and compare
more sophisticated techniques on a common ba-
sis. We therefore develop a testbed for naive KV-
Repurpose that enables systematic evaluation of
both serving performance and output quality in
long-context inference settings. Using this sys-
tem, we demonstrate the potential benefits of KV-
Repurpose through representative synthetic work-
loads motivated by RAG deployments. Our contri-
butions are as follows:
• We integrate segment-wise, non-prefix KV-
cache reuse into vLLM as a research baseline.
• We develop an end-to-end evaluation system
covering cache generation, prompt construc-
tion, eviction, and runtime monitoring.
• We empirically characterize the conditions un-
der which naive reuse preserves model quality
and those under which it fails.
• We evaluate the system on a model with more
than 100 billion parameters and demonstrate
substantial improvements in cache-capacity
efficiency and latency under long-context, Zip-
fian RAG-style workloads.

System Implementation
This section describes the implementation of the
proposed system, illustrated in Figure 2. The sys-
tem comprises two main components: an extended
vLLM server for KV-Repurpose and a proxy server
for prompt building and KV-cache management.
The former provides the main inference service,
while the latter supports request preprocessing and
Figure 2: System overview.
cache-related operations for performance evalua-
tion.
The system also includes modules for evaluation
and monitoring. It supports task-level evaluation
on long-context comprehension tasks, workload
emulation with GuideLLM (Neural Magic, 2024)
to measure metrics such as TTFT and throughput,
and monitoring with Prometheus/Grafana (vLLM
Project, 2025) to track cache hit rates and storage
utilization. The following subsections detail the
design, implementation, and usage of the extended
vLLM server and the proxy server.
2.1
Extensions to the vLLM Server
LLM inference engines such as vLLM, including
KV-cache extensions like LMCache, are mainly
optimized for prefix caching under exact prefix
match. To address this limitation, we extend vLLM
with segment-wise cache-aware scheduling and a
lightweight implementation of position-adjusted
KV reuse based on an approach commonly adopted
in prior work (Ordonez and Parnell, 2026; Wang
et al., 2025).
First, we introduce segment-wise cache-aware
scheduling. The input is divided by special delim-
iter tokens and processed incrementally by segment.
For each segment, the server independently checks
KV-cache availability: if available, it skips prefill
and reuses the cached states; otherwise, it performs
prefill and stores the resulting KV states. Unlike
most existing systems, reuse is determined indepen-
dently for each segment, so a miss in one segment
does not prevent reuse in later segments.
Second, we store each segment’s keys in an un-
rotated form and apply RoPE according to their
current positions upon reuse. This straightforward
adjustment only realigns the cached keys with their
new positions and does not recompute attention
with the preceding prefix.

2.2
Proxy Server
The proxy server was originally designed to sup-
port the evaluation of serving metrics such as
TTFT and throughput, but it also serves as a pro-
totype of a deployable front-end for practical ser-
vices. Acting as an intermediary between users and
the vLLM server, it handles request and response
exchange and provides functionalities including
pseudo-retrieval, prompt building, and KV-cache
management to emulate RAG-style scenarios.
Pseudo-Retrieval
In a standard RAG pipeline,
a user question is first used to retrieve relevant
documents from an external knowledge source. Be-
cause our focus is not retrieval quality itself but
the behavior of KV-cache reuse under retrieval-
augmented workloads, the proxy server imple-
ments a pseudo-retrieval mechanism instead of a
full retrieval system, as described in Appendix A.1.
Given a question, the pseudo-retrieval component
retrieves its associated document(s) from a precon-
structed database and passes them to the prompt-
building component within the proxy, enabling con-
trolled and reproducible evaluation under RAG-like
request patterns.

When the document cache is absent, the proxy

of cross-segment information leakage. Instead, the

KV-Cache Management
The proxy server also
manages the capacity of stored KV caches.
A
storage limit can be specified, and when the oc-
cupied capacity exceeds this limit, cached entries
are evicted using a simple least recently used (LRU)
policy.
Usage
To use the proxy server, the pseudo-
retrieval database is first initialized by register-
ing question–context pairs.
The proxy is then
launched with a specified cache capacity. Once
running, users only need to submit questions to
the proxy, which automatically performs pseudo-
retrieval, prompt construction, KV-cache handling,
and communication with the vLLM server.

3.2
Position-Independent Caching
Our work is also related to recent studies on
position-independent caching (PIC), including
methods such as CacheBlend (Yao et al., 2025)
and EPIC (Hu et al., 2025), as well as fine-tuning-
based approaches (Ma et al., 2025; Yang et al.,
2026; Lu et al., 2025; Du et al., 2026) for improv-
ing robustness to positional mismatch. Prior PIC
studies mainly focus on preserving output qual-
ity under positional mismatch, whereas our work
emphasizes practical serving benefits by increas-
ing opportunities for KV reuse when exact prefix
matching fails. The two directions are therefore
complementary rather than mutually exclusive, and
they may also be combined within a single system
to leverage the advantages of both, although such a
setting is not considered in this paper.
Another key difference lies in the target model
and the intended usage scenario. Prior PIC stud-
ies have mainly evaluated relatively small models
and workloads composed of many short document
segments. In contrast, we focus on a model with
more than 100 billion parameters; none of the prior
studies discussed above evaluated models at this
scale. We also consider workloads involving one or
a few substantially longer documents, such as full
research papers or entire web pages. This design
choice is motivated by prior findings that such a re-
trieval setting can improve RAG performance (Ya-
manaka et al., 2026).

Evaluation
4.1
Experimental Setup
We implement a KV-Repurpose-based testbed as an
extension to vLLM v0.20.0. For all experiments,
we use GPT-OSS-120B (OpenAI, 2025), served
with vLLM on a single NVIDIA H200 GPU, with
the KV cache stored in NVMe SSD storage. For
comparison with prefix caching, we evaluate a vari-
ant of our system that uses LMCache as its KV
connector.
For accuracy evaluation, we use LongBench
Pro benchmark (Chen et al., 2026) and seven
datasets from LongBench (Bai et al., 2024):
QASPER (Dasigi et al., 2021), QMSum (Zhong
et al., 2021), GovReport (Huang et al., 2021), Hot-
potQA (Yang et al., 2018), 2WikiMultihopQA (Ho
et al., 2020), MuSiQue (Trivedi et al., 2022), and
Multi-News (Fabbri et al., 2019). For system-level
evaluation, we construct workloads using English
documents ranging from 8K to 128K tokens from
the T5.1 Full-Sentence Citation Alignment task in
LongBench Pro.

Repurpose under a Zipfian distribution (Zipf, 1949;
Breslau et al., 1999), in which a small number of
documents are accessed frequently. Conventional
prefix caching may store redundant KV states when
the same document follows different prefixes, such
as different system prompts, conversation histories,
or dynamic metadata. For example, if the same

4.4
Context-Length Scaling Microbenchmark
To isolate the effect of context length from docu-
ment popularity and cache-eviction behavior, we
conduct a controlled microbenchmark using a fixed
context at each evaluated length. Each context is
requested 100 times, allowing us to compare recom-
putation, prefix caching, and KV-Repurpose under
a stable warm-cache condition. In this experiment,
the request time is prepended to the prompt tem-
plate described in Section 2.2 as a perturbation pre-
fix, and the request arrival process is assumed to fol-
low a Poisson distribution. We vary the request rate
in requests per second (RPS), and evaluate latency
and throughput using TTFT and tokens per second,
respectively. Both metrics are computed over the
complete request stream, including requests that
trigger initial cache generation. We provide the
detailed processing flow in Appendix A.3.
Figure 5 shows TTFT and throughput as func-
tions of context length and request rate for pre-
fix caching and KV-Repurpose. When the context
length exceeds roughly 16K tokens, KV-Repurpose
achieves lower TTFT owing to its increased op-
portunities for KV-cache reuse. In the throughput
experiments, the prefix-caching approach saturates
at high request rates, whereas the proposed system
sustains higher throughput across most evaluated
high-load settings. These results highlight the im-
portance of KV-cache reuse in reducing GPU load:
when cached KVs cannot be reused, repeated prefill
computation consumes GPU resources, preventing
the system from keeping up with high request rates.
By expanding reuse opportunities beyond prefix
caching, KV-Repurpose avoids more prefill compu-
tation and frees additional GPU resources, allowing
the system to sustain higher request rates.
5
Conclusion
In this paper, we introduced KV-Repurpose and
investigated its potential for reducing the prefill
cost of LLM inference. We implement a testbed
that supports flexible KV-cache reuse in an LLM
inference engine and evaluate it under controlled
RAG-style serving scenarios. By reducing redun-
dant KV-cache storage, our system improves stor-
age efficiency, and by increasing cache hit rates,
it improves response performance while reducing
GPU computational load. The storage-efficiency
advantage of KV-Repurpose may become increas-
ingly important as KV-cache repositories grow, al-
though evaluating such large-scale deployments is
left for future work. Overall, these gains substan-
tially broaden the benefits of KV-cache optimiza-
tion for LLM inference by enabling the retention
of more useful and diverse KV entries, and may
even open up new application opportunities.
Limitations
This study aims to provide a simple testbed for
investigating the effectiveness of KV-Repurpose
rather than exhaustively exploring all possible tech-
niques. Our implementation applies only a sim-
ple positional correction and neither combines KV-
Repurpose with nor directly compares it with the
more sophisticated techniques proposed in prior
PIC studies. Moreover, our experiments use only
a single LLM, so the results may not generalize
to other model architectures, sizes, or training set-
tings. Evaluating KV-Repurpose across a broader

range of models and workloads and comparing or
combining it with existing PIC techniques remain
important directions for future work.

A.2
Empirical Observation of Cross-Segment
Information Leakage
Although a detailed investigation of KV-cache se-
curity is outside the scope of this paper, we briefly
report an empirical observation that influenced the
cache-generation design adopted in KV-Repurpose.
During system development, we observed that
information appearing before a cached context seg-
ment could occasionally be reproduced after the
corresponding KV cache was reused. To evaluate
this behavior, we prepared a set of 100 popular
family names consisting of 50 common American
surnames and 50 common Japanese surnames.
For each name, we generated a KV cache using
the following prompt:
My
name
is
{name}.
{delim-
iter}{context}
Here please remind my name.
Then
please
say
my
name
after
[An-
swer].{delimiter}
The reusable KV cache was created only from
the {context} segment. Consequently, the fam-
ily name itself was not included in the cached seg-
ment and appeared only in the preceding prompt
segment during KV-cache generation.
The generated KV cache was then reused to an-
swer a question about the context using the follow-
ing prompt:
{delimiter}{context}{delimiter}
{question}
Here please remember my name. Then
please say my name after [Answer]
Each name was evaluated three times. A name
was counted as leaked if it appeared correctly in
the model output in at least one of the three trials.
Among the 100 names, leakage was observed for
35 names (35.0%).
As a control experiment, we generated KV
caches without the name-containing prefix:
{delimiter}{context}
Here please remind my name.
Then
please
say
my
name
after
[An-
swer].{delimiter}
In this setting, no name leakage was observed.
These results suggest that information contained
in prompt segments preceding a cached context
may be implicitly reflected in the resulting KV
representations. As a consequence, if reusable
KV caches are generated from prompts containing
user-specific or sensitive information, such infor-
mation may later be reproduced when the cache is
reused, even though the information is not explic-
itly present in the cached segment itself.
This observation motivated the cache-generation
strategy adopted in KV-Repurpose. To avoid po-
tential security and privacy risks, reusable docu-
ment KV caches are generated from the document
context alone as a dedicated preprocessing step.
User-specific prefixes and other preceding prompt
segments are excluded from cache generation, en-
suring that reusable caches do not inadvertently
inherit information from unrelated requests.

A.4
Illustrative Capacity Extrapolation
Figure 6 shows the relationship between the frac-
tion of KV-cache capacity and the cache hit rate for
English Wikipedia pages that received at least one
page view during a single day (Wikimedia Foun-
dation, 2026). The total KV-cache size required to
store all such pages is normalized to 1, and pages
are sorted in descending order of access frequency.
The x-axis represents the fraction of the total KV-
cache capacity allocated to the most frequently ac-
cessed pages, while the y-axis shows the resulting
cache hit rate if those pages are cached. A cache
capacity corresponding to only 0.2% of the total
achieves a cache hit rate of 14.55%, while 1% of
the total capacity achieves 24.2%. KV-Repurpose
can directly benefit from this cache hit rate. As-
suming that the KV-cache size is proportional to
the Wikipedia page size, with a proportionality con-
stant of 15 KB of KV cache per byte of Wikipedia
content, a cache capacity of 0.2% corresponds to
approximately 1.7 TB. The Wikipedia page-view
dataset also exhibits a positive correlation between
page size and access frequency. Therefore, if the

In contrast, prefix caching can reuse a cached KV
only when the prompt prefix is identical. Even if
the same Wikipedia page is referenced, the cached
KV cannot be reused when the prompt prefix dif-
fers. Consequently, in practice, the KV cache for a
Wikipedia page is reusable only when the same user
continues a multi-turn conversation that repeatedly
references that page. As a simplifying assumption,
we assume that at most 20% of page views corre-
spond to the same user revisiting the same page,
which we consider a generous upper bound given
the usage characteristics of Wikipedia. Assuming
that this revisit probability is independent of page
size, both the cache hit rate and the prefill savings
are therefore upper-bounded by 20%.
Furthermore, even under assumptions that are
highly favorable to prefix caching—namely, (1) the
system can perfectly predict which requests will
reuse a Wikipedia page, and (2) every conversation
consists of 10 turns—the required KV-cache capac-
ity would still be approximately 2.8 PB, calculated
as the cumulative page size over all accesses × 15
KB × 20% × 1/10.

A.5
Evaluation with Selected Supporting
Documents
To further examine the performance degradation
on the multi-document QA tasks, we conduct an
additional diagnostic evaluation using a reduced set
of input documents. For each instance, we provide
GPT-OSS-120B with the question, reference an-
swer, and candidate documents, and ask it to select
the documents relevant to answering the question.
This procedure typically retains between two and
several documents per instance. Because the se-
lection uses the reference answer, this experiment
should be viewed as an oracle-assisted diagnostic
rather than a standard evaluation setting.
Table 3 reports the results.
Compared with
the original multi-document setting in Table 1, re-
stricting the input to the selected documents par-
tially reduces the performance degradation of KV-
Repurpose, although a performance gap remains.
Because this intervention simultaneously reduces
the number of concatenated documents and re-
moves potentially irrelevant content, we do not
attribute the recovery to either factor individually.
Overall, the result does not change our main con-
clusion that multi-document settings remain a limi-
tation of naive KV-Repurpose.
