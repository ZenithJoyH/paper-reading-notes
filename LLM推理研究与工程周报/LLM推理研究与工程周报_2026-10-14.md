## 1. Improve TTFT for Multi-Turn Agentic Workloads with Bi-Directional KV Transfer in vLLM

**日期与来源**：官方博客发布于 **2026-10-12**；旧功能在本周出现详细工程分析、H200 实测及复现说明，因此纳入，而不把它说成本周首次发明。[原文](https://vllm.ai/blog/2026-10-12-bidirectional-kvxfer-multiturn-agentic-workload)｜[vLLM 代码](https://github.com/vllm-project/vllm)｜[会话代理](https://github.com/vllm-project/vllm/blob/v0.29.0/examples/disaggregated/disaggregated_serving/disagg_proxy_multiturn.py)｜[多轮 benchmark](https://github.com/vllm-project/vllm/tree/v0.29.0/benchmarks/multi_turn)｜[流式 KV 元数据 PR #40186](https://github.com/vllm-project/vllm/pull/40186)。

### 核心结论与机制

**作者声明**：传统 P/D 分离只做 P→D 传输。D 生成的响应 KV 在下一轮 P 无法使用；P 端缓存淘汰或换路由节点后还可能重算整段历史。双向方案让 D 保留已完成会话的 KV，通过流式响应末尾返回位置元数据；有状态代理按 `conversation_id` 保存元数据，下一轮 P 先检查本地前缀，再按阈值向 D 发起异步 NIXL READ，随后仅计算未命中后缀。KV 张量直接在节点间传输，不经过代理。

默认 `decoder_kv_blocks_ttl=480` 秒，固定计时、不自动续期；默认 `kv_recompute_threshold=64` tokens。过短可复用前缀可能因网络和协调开销而适合重算；过期则走常规 prefill。作者称在 Trainium/EFA 上最初构建验证，但本篇可引用性能数据来自 H200，**没有公布 Trainium 同口径数值**。

### 适用范围、限制与复现条件

适合历史反复发送、轮间隔小于 TTL、P 本地缓存不稳定、网络回读便宜的多轮 agent/会话。首轮、无共享历史和短前缀场景未证明获益；D 端保留 KV 会挤占活跃请求容量。源端重启、会话分叉、代理重启、TTL 过期和网络失败的尾时延/恢复情况尚缺实测。

**本报核查**：官方附录的 [run_multiturn_sweep.sh](https://vllm.ai/assets/repro/2026-10-12-bidirectional-kvxfer-multiturn-agentic-workload/run_multiturn_sweep.sh) 在本次读取中返回 404 页面，因此没有拿到负载生成参数；另外两个附带脚本未逐一验证。正文的版本、命令、代理和 benchmark 路径仍提供重建入口，但不能称为“一键完整复现”。#40186 是旧 PR，日期不能算本周新提交；复现时应固定其 patch/hash 并检查安装版本是否已含所需字段，不盲目对滚动 main 打补丁。

**本报推断**：异构平台真正可迁移的是“远端 KV 回读成本与本地重算成本的交叉点”及元数据/保留语义，不能由“accelerator-agnostic”推定任意 NPU 的 connector、KV layout 或驱动均可直接使用。

## 2. Compositional Performance Modeling of LLM Inference Clusters with Hierarchical KV Caching

**日期与版本**：**2026-10-11**，arXiv **2610.15366v1**；Ruiyang Ma、Sheng Qi、DaiKang Kuang、Teng Ma、Guojie Luo，主要来自北京大学。[摘要/日期](https://arxiv.org/abs/2610.15366v1)｜[PDF](https://arxiv.org/pdf/2610.15366v1)｜[全文](https://arxiv.org/html/2610.15366v1)。**作者实现代码链接未找到**；[SGLang](https://github.com/sgl-project/sglang) 是被测框架，不冒充论文实现仓库。论文未给出 SGLang、HiCache、CUDA、通信库或 simulator 固定提交。

### 核心结论与机制

**作者方法**：把本地算子/整轮服务成本与集群资源、KV 状态分开。先在 1P1D 校准 prefill、decode、P/D 交接和 H2D/D2H；离散事件模拟器在 KV 容量、传输资源和队列约束下组合这些成本，再扩大为 3P1D。

三条缓存转移不变量特别适合移植到测试用例：**转移前预留目的容量；转移/使用期间保护源副本；完成后目的副本才对计算可见**。prefix hit 也要等拉取和设备容量就绪，不能将命中视为零时延。

Prefill 区分新计算 tokens 和已缓存但仍参加 attention 的上下文；decode 按 graph bucket 建模 padding 与 context 成本；P/D 交接拟合有效完成时间，包含软件协调，不能用 NIC 标称带宽代替。多源向 D 传输采用共享速率假设，需要在目标系统重新校准。

### 公开实验设置

| 条件 | 已披露内容 |
| --- | --- |
| 硬件/卡数 | RDMA 连接的 NVIDIA **L20Z** hosts；每 worker 2 GPU、TP2；1P1D=4 GPU，3P1D=8 GPU（卡数由 worker 数×2 推得，物理主机映射未明确） |
| 模型/精度 | Qwen3-8B、Qwen3-32B；**BF16 KV**；权重/activation 精度未明确披露，不能由 KV 精度补推 |
| 缓存/调度 | 每 worker 262,144 device KV tokens；每 P 524,352 host KV tokens；page 64、prefill chunk 4,096、每 worker 最多 32 running requests；RR 路由；D prefix/host cache 和 L3 关闭 |
| QA 负载 | QASPER：506 请求、129 组，平均 5,449.8/128 input/output；SQuAD：400 请求、71 组，平均 226/128 |
| Coding 负载 | 50 完整 session、451 请求，平均 13,325.4/650.4 tokens；保留原请求/输出长度并缩放 interarrival |

### 关键结果：实测、误差与模拟必须分开

**作者实测校准/验证**：QA E2E 预测 MAPE 平均 **1.34%**；Coding **6.36%**，适配 LLMServingSim Coding 为 **15.21%**。这描述预测误差，不是时延降低。

| 组别 | E2E MAPE：本文/基线 | TTFT MAE：本文/基线 | TPOT MAPE：本文/基线 |
| --- | --- | --- | --- |
| QA 8B 1P1D | 1.55% / 5.25% | 15.4 / 33.6 ms | 1.20% / 0.47% |
| QA 32B 3P1D | 1.16% / 3.30% | 24.7 / 61.1 ms | 0.34% / 0.74% |
| Coding 8B 3P1D | 9.07% / 16.90% | 155.1 / 681.1 ms | 2.98% / 5.64% |
| Coding 32B 3P1D | 4.88% / 15.16% | 215.1 / 2,118.9 ms | 1.69% / 4.37% |

摘录 table IV 代表行，其余见原文；QA 8B 的 TPOT 预测并非本文更优。不能将 MAE/MAPE 填作实际 TTFT/TPOT。[实验全文](https://arxiv.org/html/2610.15366v1#S5)

**作者公开实测的工程反例**：3P1D coding，8B=0.5 req/s、32B=0.25 req/s，从空 cache 开始，每策略只测一次；session affinity 相对 RR 将未缓存输入减少 **48.2%/46.1%**，但平均 E2E 反而变化 **+0.44%/+1.32%**。共享 D 的生成需求未减少。命中率或 prefill 节省不能充当用户体验结果。

**仅模拟**：60s idle TTL 相对 LRU，8B/32B 时间加权 KV 占用下降 **86.9%/92.9%**，mean TTFT 增加 **7.4%/3.8%**。减少的是已用 KV slots，**allocated GPU memory 不变**，不是显存分配减少 90%。

**周转收益**：CPU 模拟相对真实 replay 平均 **15.33×**；replay 包含原定 arrival gaps，启动和校准不计入。不是 GPU 推理提速。

### 适用场景与边界

适合先筛 P:D 比例、路由亲和性、host cache 与 TTL 参数，再用真机确认。**本报推断**：异构测试可为每种卡、通信路径、graph bucket 分别建立 profiles；不能直接复用 L20Z 拟合参数到昇腾、MUSA、ROCm 或混合卡集群。

局限：只验证两个模型、同类硬件和有限拓扑；coding 数据参与机制开发，32B prefill 有开发数据复用；decode 因扩大 KV pool 做了重校准；L3 没有实测；缓存容量与路由模型、基线改动混在比较中，不能把误差改善全部归功单一机制。小均值误差不能保证 P99、故障恢复或稳定性预测。无作者代码和固定软件版本，应以方法验证为主，降低精确复现优先级。

## 3. vLLM-Ascend v0.30.0rc1/rc2：缓存格式、runner 与并行组合的测试价值

**原文/版本**：[v0.30.0rc1 release，2026-10-12](https://github.com/vllm-project/vllm-ascend/releases/tag/v0.30.0rc1)，提交 [5f828ad638ee4f9b12db87f9d5481f29076d37f9](https://github.com/vllm-project/vllm-ascend/commit/5f828ad638ee4f9b12db87f9d5481f29076d37f9)；[rc2，2026-10-13](https://github.com/vllm-project/vllm-ascend/releases/tag/v0.30.0rc2)，提交 [8fde6d4e335fe300e2b949aab0e31659cce0811d](https://github.com/vllm-project/vllm-ascend/commit/8fde6d4e335fe300e2b949aab0e31659cce0811d)。[版本文档](https://docs.vllm.ai/projects/ascend/en/v0.30.0rc1/)｜[代码](https://github.com/vllm-project/vllm-ascend/tree/v0.30.0rc1)。

这是一项**实现/兼容性进展**，入选理由是能直接导出缓存与通信测试矩阵；不是发布性能冠军，也不展开国产生态周报常见的模型支持清单。

### 最有价值的机制与代码证据

1. **TurboQuant 4-bit latent KV 扩展至 MRV1 的 SFA 路径**。[PR #18048](https://github.com/vllm-project/vllm-ascend/pull/18048) 于 **10-09 合并**到 release branch；代码提交 [54e3de4f7ddd28222e842755eab0c232638723da](https://github.com/vllm-project/vllm-ascend/pull/18048/commits/54e3de4f7ddd28222e842755eab0c232638723da) 标为 10-08。[diff 与单测](https://github.com/vllm-project/vllm-ascend/pull/18048/files) 可以核对缓存规格和单 tensor 分配，不只看功能名。
2. 针对 `kv_lora_rank=512`、RoPE dim=64，slot 为 **386 bytes**：256 bytes int4 latent +128 bytes BF16 RoPE +2 bytes FP16 scale。以 `torch.int8` 承载 packed bytes，不是所有 KV 都变成 4 bit；“4-bit”不能等同整个 KV pool 压缩 4×。独立 indexer/cache、页对齐、混合模型状态还占空间。
3. MRV1 的 SFA 配置可以使用 `turboquant_4bit_nc`，**DeepSeek V4 压缩缓存路径仍要求 MRV2**；约束包括 BF16、上述维度、A2/A3、支持的 sparse 模型，且不与 xLite/C8 混用。PR 作者明确说明：相关单测不是 e2e，PR CI 缺少 TurboQuant e2e，依赖带 `cann_ops_nn.turbo_quant` 和 `key_quant_mode=3` 的 sparse attention 算子。
4. release 还覆盖 MooncakeConnectorV2、KV Pool、host/SSD pooling、PCP/DCP 与 graph 元数据及 hybrid cache 修复。值得验证的是“缓存被重分配/转移/抢占后，scale、block table 和 recurrent state 仍对应正确请求”。不要直接打开所有组合后用一次吞吐测量证明兼容。

以上为作者声明和代码/单测证据，**没有给出可引用的同条件 TTFT、TPOT、P99、输出/总 tokens/s 或精度保持率**。也没有完整已披露 benchmark 的 ISL/OSL、并发/请求率和基线。因此不推算部署提速。硬件支持表提到 Atlas 800I A3（GLM 项为 128GB×8）、A2 和特定 Qwen 的 310P 路径，这是支持范围，不能当实际性能实验的硬件/卡数。

### 多机稳定性检查的具体线索

[Issue #18209，10-10，10-12 有维护者回复](https://github.com/vllm-project/vllm-ascend/issues/18209) 指出 fine-grained TP 的 rank reshape 与实际 DP/PP/PCP 布局可能不一致，存在 PP>1 collective 跨 stage 的 silent hang 风险。证据来自 **静态分析，作者明确没有硬件复现**；针对 main @ [91db8b30637c7c923a4ee0fa2b4df01c531ac837](https://github.com/vllm-project/vllm-ascend/commit/91db8b30637c7c923a4ee0fa2b4df01c531ac837)，本次读取 issue 仍 open、关联 #18373。不推定所有 release 都复现，也不推定关联 PR 已合入修复。

## 4. Rubin 上的 SGLang/vLLM：选可迁移的瓶颈分析，不把跨代倍率当软件收益

**本周两份一手报告**：[SGLang and Miles on NVIDIA Vera Rubin，2026-10-09](https://www.lmsys.org/blog/2026-10-09-vera-rubin)；[vLLM Support for NVIDIA Vera Rubin NVL72，2026-10-09](https://vllm.ai/blog/2026-10-09-vera-rubin-preview)。[SGLang 代码](https://github.com/sgl-project/sglang)｜[vLLM 代码](https://github.com/vllm-project/vllm)｜[FlashInfer](https://github.com/flashinfer-ai/flashinfer)｜[MSA](https://github.com/vllm-project/MSA)｜[Humming](https://github.com/vllm-project/humming)。

### SGLang：隐藏拷贝、融合与流水深度

**作者实测/声明**：2 个 Rubin 节点、合计 **8 GPU**，Kimi K3 **NVFP4**，69 KDA/24 MLA attention layers，92 MoE layers，DSpark draft-and-verify；部分 attention 测试明确 FP8 KV。推理 stack 的 SGLang、CUDA、PyTorch、DSpark checkpoint revision、kernel 固定提交没有披露；文中 Miles #3700 是 RL enablement，不能作为所有推理优化代码定位。

| 优化 | 数据、测试点与指标性质 | 限制 |
| --- | --- | --- |
| MLA 加深 K/V 读取流水 | Rubin CTA SMEM 327 KiB，相对旧 227 KiB；从 3K/2V stages 到 4K/4V；batch16、128k context，MLA **快16%**，作者称输出 bit-identical | attention 内核收益，未给绝对 ms 或 E2E 同点收益 |
| split-KV reduction 先发全部 load，再寄存器累加 | batch1、128k context，full FP8 MLA **快20%** | 内核收益；需要确认寄存器压力与 split 数 |
| 32→64 split-KV | K3、FP8 KV，作者称 **E2E 改善1.9%** | 完整 E2E 负载/ISL/OSL/请求率未披露 |
| FP8 saturating conversion | preparation kernel **2.5×** | 溢出从 NaN 改为 ±448 clamp，数值语义改变，不能笼统称无损 |
| MoE finalize+shared expert+all-reduce+RMSNorm 融合 | 8 GPU，每 decode step 去除 **276 launches**，**E2E 改善5.9%** | 未给完整负载、绝对时延和 P99 |
| push all-reduce crossover→256 rows | **32 concurrent requests**，decode throughput **+3.6%** | ISL/OSL、输出/总 tokens/s 绝对值未披露；硬件相关阈值 |
| latent all-gather GEMM 的算术上 tensor core | 4—8 rows，decode step time **降低1.1%** | 不是独立新增1.1×；通信与算术贡献需拆分 |
| KDA verify 减 barrier、warp register 保存权重 | production verify kernel **快20%**，作者称 bitwise identical | 内核收益 |
| norm kernel 直接读 strided gate | 原隐藏 contiguous copy **2.6μs×69/step**；decode step time **降低1.8%** | profiling 方法迁移价值高；不保证其他模型有同样 copy |

各项对照其原实现，不能相加成一个总提速。除指定 batch/context/concurrency，完整 serving ISL/OSL、请求率、TTFT、TPOT/ITL、P99、绝对输出/总 tokens/s 没有披露。文中引用 Cognition 私有 SGLang fork 的总 tokens 吞吐最高 **4.8× GB200**，不计为公开可复现框架收益。

**本报推断**：strided tensor 支持、消除 host sync/临时 copy、collective 尾部融合的诊断方法可迁移到 NPU/ROCm/MUSA；327 KiB SMEM、212 SM、NVLink6、packed FP8 instruction 和阈值本身不能直接移植。

### vLLM：局部性 MoE 的有效对照，比 7.84× 更可解释

**作者机制**：CUDA 13.4 locality domains 把 SM 与本地 HBM 对应，FC1/FC2 按 split-N 划分权重，green contexts/streams 启动局部计算，减少跨 domain 取权重。小 token decode 主要受权重读带宽限制。

**作者内核实测**：MiniMax M3 shapes，在 Rubin 上比较 non-localized/localized；TP2/TP4/EP2/EP4；图表覆盖 12 个 token counts；固定 kernel configs、balanced routing、HBM **4752 MHz**、CUDA Graph timing、**5 repeats 均值**，各档 speedup 用几何平均。默认只使用 200/212 SM，backfill 可使用全部 212。作者概括约 **1.2×** 小 token MoE layer FC1+FC2 改善，TP2 backfill 展示约 **1.18×**。**不含通信时间**，未披露该内核对照的完整权重/activation 精度和端到端 TTFT/TPOT/P99。

**版本/依赖**：报告指向 CUDA **13.4**、PyTorch **2.15**、FlashInfer **0.7.0** 与 `vllm/vllm-openai:cu134-nightly`，给出的镜像 digest 为 `sha256:5f74ee1fb3cec4f248e5ac3ad57d05c5a1af70c61787821795137372865e84fd`。[镜像链接](https://hub.docker.com/layers/vllm/vllm-openai/cu134-nightly/images/sha256-5f74ee1fb3cec4f248e5ac3ad57d05c5a1af70c61787821795137372865e84fd)。nightly 标签滚动更新，复现应固定 digest；blog 未给具体 vLLM commit，且“fully enable locality domains”仍列为下一步，不断言稳定版本已默认开启。

**公开跨代图的准确口径**：[AgentX 图](https://vllm.ai/blog-assets/figures/2026-10-09-vera-rubin-preview/agentx-results.png) 标注更新 **2026-10-08**，模型 MiniMax M3 **428B**，纵轴 **Agentic Token Throughput per Chip (tok/s/chip)**，横轴 **P90 Interactivity (tok/s/user)**，Dynamo+vLLM。Rubin 多个 TP2 点及 `1×TP2+4×TP2` 点，GB200 则有 TP4/TP8 点；图写明 official preview、结果可能随验证变化。作者称匹配 interactivity 最高 **7.84×**，150 TPS 约束下 **5.18×**。不是已披露的固定 4k/1k 或 64并发对照；没有逐点请求率、精度、模型 revision、全部软件版本和确切参与 GPU 数。NVL72 是平台名称，不能据此声称每个点用了 72 卡；也不能把 agentic throughput 自动标为 output-only tokens/s。

MLPerf Qwen3-VL-235B-A22B 对 GB300 最高 **3.7×** 属另一 VLM 负载，本期未完整核对其提交配置，不用于推荐收益或横向排名。跨代硬件、并行策略和内核栈共同改变，不能归因为单个 vLLM 优化。

**适用边界**：局部性方法值得在有非均匀设备内存/多 die 结构的平台验证；需支持内存 placement、计算 affinity 和相应 graph/collective。不能仅按“有更多 HBM”就假设有效。当前报告未证明真实不均衡 routing、跨机 EP 或故障重试下的局部性收益。

## 最值得进一步验证的 3 个方向

以下全部为**建议实验**，不是上述论文/博客已有实测，也不是本报已运行的结果。优先级按现有异构平台能否完成最小可解释对照排列；如果国产平台 connector 不支持双向回读，先做同节点亲和性/保留实验，不强行实现整套机制。

### P0：多轮 KV 复用的成本交叉点与保留策略

- **最小对照**：固定模型、精度、卡数、P:D、并行配置和 arrival trace；采用 2×2 因子：P prefix cache 开/关 × 双向回读开/关。所有组从空 cache 起步、相同历史 tokens；分别测试 RR 与 session affinity，单独比较 TTL，不同时改变多个策略。
- **建议负载**：单请求形状 4k input/1k output、16k/1k；共享前缀比例 0/50%/90%；多轮逐步增长历史。并发 **1/4** 用于低并发 TTFT/TPOT，**64** 用于容量/排队测试；若每 worker 限制 8/32，则显式记录 64 offered concurrency 与 admission queue，不冒称 64 同时运行。轮间隔建议 1/10/60/300/600s，覆盖 TTL 前后。
- **依赖**：可用的 NIXL/Mooncake/目标平台 KV transfer；权重、tokenizer、KV layout、page size 与量化 scales 一致；会话 ID、流式末尾 metadata、互联和注册内存可观测。跨不同平台搬 KV 需额外验证 tensor layout/dtype，不能由“异构”二字默认兼容。
- **机制判据**：分别计时重算、D→P transfer、代理/等待；阈值处应满足 transfer+协调成本小于免掉的重算成本。扫描可复用长度 64/256/1024/4096，threshold 根据实测拟合，不照抄64。
- **预期收益**：长会话且 P miss 时可能降低 TTFT/重复 prefill 工作；不承诺任何倍率。共享 D 饱和时可能只降计算成本、E2E 不改善，TTL 过长还可能恶化 P99。
- **正确性/稳定性**：冷缓存、回读、过期重算三路径比较输出与 logits；测试 prompt 改写、会话分叉/并发同 ID、cancel、D/代理重启、网络超时、过期 metadata、缓存抢占和 OOM 压力。核对源保护、目的预留、完成后可见与失败回退；故障后不读旧 block、无资源泄漏。
- **指标**：TTFT/TPOT/逐 token ITL 的 P50/P90/P99、E2E、output tokens/s、input+output tokens/s、SLO goodput、有效 KV bytes/s、命中/重算 tokens、设备/host 占用、错误与重试。SLO 与总 tokens 计数方式预先固定。

### P1：隐藏拷贝、同步与通信尾部——可迁移的低并发优化

- **最小对照**：先以目标平台 profiler 找 `contiguous`、D2D/H2D copy、host sync、launch gap 和 collective tail。固定 rank 布局，先将一个 norm/gate 内核改为读 stride，再单独测试 finalize+residual/shared expert+collective+norm 融合；每次仅改一处。
- **建议负载**：4k/1k、16k/1k；并发1/4/64；微基准使用实际捕获的 M/N/K/stride、dtype、routing 分布。分别 eager/graph，对 graph bucket 的边界和 padding 加测试；长上下文 attention 可补128k，但需具备模型和容量。
- **依赖**：profiler 与设备 timeline、内核编译工具、stride-aware 算子、通信接口；国产平台需使用其 graph/collective 能力，不能直接替换 CUDA API。若做 NUMA/locality，另需内存 placement 和执行 affinity。
- **预期收益**：减少小 batch launch/copy 固定成本；端到端收益可能只有个位数百分比，SGLang 的1.8%/5.9%不能移植为预期实测。collective 占比高、融合导致占用下降或 routing 不平衡时可能无收益。
- **正确性/稳定性**：非连续输入、混合长度、zero-token rank、异步流依赖、graph replay、PP/EP 边界；lossless 优化设明确 logits 容差，并检查 deterministic 输出。FP8 saturation 必须单独核对 NaN/Inf/clamp、overflow 数量和质量，不能并入 bit-identical 声明。
- **记录**：内核与 decode step 绝对时长、launch/copy数、通信时间、P99、tokens/s、显存；交替 A/B、暖启动后至少3个独立重复，冷启动/编译时间另报，不把最佳单次当结论。

### P1/P2：Ascend packed KV + runner/graph/parallelism 的最小兼容矩阵

- **启动门槛（P0）**：先固定 rc2 image digest、HDK/CANN/torch_npu/算子包；检查 TurboQuant operator 是否存在及支持维度。设备不是A2/A3、维度不符或模型路径未声明支持，则不运行性能推论。
- **最小对照（P1）**：对一个支持的 SFA 模型，在同一 runner/同一图配置下比较 BF16 main KV 与 packed4bit；再分别比较 MRV1/MRV2（仅支持路径）、eager/graph。DeepSeek V4 不做不存在的 MRV1 TurboQuant 组合。先单机，后1P1D，再加PP/DCP/EP；每一步保留可工作基线。
- **建议负载**：4k/1k、16k/1k、并发1/4/64；混合长度、prefix hit/miss、page recycle、preempt/resume；PP2、DP2 的 rank layout 可先做无需大模型的配置/group 校验，真实 collective 则必须真机。
- **预期收益**：首先检验主 cache bytes/token 与可接纳并发；总 pool 节省取决于RoPE、scale、indexer、混合状态和padding。量化/解量化开销可能抵消带宽收益；没有端到端数据，不设提速倍率。
- **正确性检查**：BF16 logits/perplexity、长上下文检索与任务质量基线；提前规定质量阈值；核对 scale 在page reassignment后恢复、Mamba/recurrent状态、DSpark rejection/seq_len边界。量化配置不能要求输出逐 token 完全一致，也不能只看服务启动成功。
- **稳定性检查**：rank group集合正确且 unsupported combination fail-fast；PP×fine-grained TP 静态线索需真机回归；网络 receive failure、cache pool初始化、睡眠/唤醒、重启与OOM后恢复；建议1小时压力筛查后对候选做8小时持续运行，记录超时、挂起、错误、内存漂移和P99。时长为测试建议。
- **边界**：release支持表、RC状态、MRV2 opt-in、相关开放精度issue都应保留在实验记录中；不以一次更高tokens/s证明多机稳定。

## 通用测试记录模板

每组保存：加速器精确型号/板卡数/内存、CPU NUMA/驱动、机器与NIC拓扑/有效带宽、模型权重和tokenizer revision/hash、weights/activation/KV/draft精度、engine/plugin/编译器/通信库 commit与镜像digest、TP/PP/DP/EP/PCP/DCP、graph bucket、page/chunk/内存池、缓存初始状态、prefix/session规则、实际输入输出tokens分布、offered concurrency/请求率/arrival生成器、warmup与独立重复、基线唯一变更点。
