## 1. HAWK: Heterogeneity-Aware KV Cache Transfer for Efficient GPU-NPU Phase-Disaggregated LLM Inference

**发布日期／版本**：arXiv **2610.29873v1**，2026-10-21 15:25:35 UTC，即北京时间 **10-21 23:25:35**。

[论文信息](https://arxiv.org/abs/2610.29873v1)｜[在线全文](https://arxiv.org/html/2610.29873v1)｜[在线PDF](https://arxiv.org/pdf/2610.29873v1)｜[中文论文笔记](论文笔记/2026-10-23/HAWK_summary.md)。作者为Junhyeok Park、Jungeun Yoon等，主要来自ETRI。**HAWK专用代码未发布**，论文仅表示计划开源；[Mooncake](https://github.com/kvcache-ai/Mooncake)和[Tenstorrent软件栈](https://github.com/tenstorrent/tt-metal)是依赖，不能当作HAWK实现。

**核心结论与机制。** GPU/NPU分离的成本不只在网络：相同逻辑KV张量可能具有不同tile、padding、bank分布和地址映射。HAWK为NPU驱动补充peer-memory支持，建立NIC直接访问设备内存的RDMA路径；按目标NPU的DRAM channel分配布局感知buffer。P侧先把KV重排成每个目标channel对应的大连续片段，再批量传到多个目标buffer，在搬运时完成余下布局对齐。它保留P侧变换和device buffer拷贝，不能称为完全零拷贝；也不是上期NIXL Push的提前注册方案。

**作者公开实测条件：**

| 项目 | 已披露配置 |
| --- | --- |
| P/D | 1P1D，各TP4；P为4×A100 PCIe 40GB；异构D为4×Tenstorrent p150a；同构D基线为4×A100 PCIe 80GB |
| 网络 | 两机、每机ConnectX-6，200Gb/s HDR InfiniBand |
| 模型／精度 | Llama3.1-70B，论文列权重148GB；weight/activation/KV dtype没有逐项明确，不按大小推断精度 |
| 软件 | vLLM0.10.0；Mooncake Transfer Engine0.3.6；Tenstorrent用户态驱动0.68.0、内核驱动2.5.0，均有作者改动；完整镜像、TT模型栈commit未锁定 |
| Chatbot | ShareGPT；输入mean/P90为783/899，输出140/148 tokens |
| Summarization | LongBench；输入mean/P90为2186/2860，输出86/115 tokens |
| 压力／SLO | Poisson到达率扫描；客户端并发未明确。Chatbot TTFT/TPOT SLO=2000/200ms；Summarization=15000/200ms；比较90%同时达标时的输出吞吐 |
| 基线 | GPU/GPU host staging、GPU/NPU host staging、GPU/GPU direct RDMA、GPU/NPU HAWK |

**关键数据：**异构HAWK相对A100同构direct RDMA，90% SLO达标点的输出吞吐分别低 **0.48%／7.88%**；Chatbot两者可到 **0.65req/s**，Summarization异构 **0.60req/s**、同构 **0.65req/s**。文中P90 TTFT单项达标请求率差为2.90%／5.90%，不能与同时TTFT+TPOT达标点混为同一口径。未给可完整重用的逐点TTFT/TPOT绝对数表；ITL、P99及total tokens/s未披露。另一个替换D为H100的实验见Table9，HAWK输出吞吐89.69／50.75 tokens/s，对照95.96／54.28；不与A100基线交叉拼接。

10—1280MB传输微基准中，作者报告大传输下接近GPU direct路径；这是“请求KV到写入cache pool”的传输计时，不是模型TTFT。普通连续NPU RDMA buffer原型因bank不均衡／碎片化在服务中OOM，未纳入量化对照；因此尚缺成功运行的“仅direct RDMA、无布局感知”的完整消融。

**限制与复现。** 单模型、固定设备映射、需要修改底层驱动，不能直接套到昇腾或其他NPU。宣称最高1.26×能效使用ASIC功率：NPU读core监控，GPU由板卡功率结合NVBit和功率模拟器估算ASIC部分，非整机墙上功率实测。最高1.72×成本效率基于设备价格估算，非云租赁账单。实际部署应优先验证布局正确、buffer生命周期、bank占用和转移完整路径。

## 2. Announcing Humming: Fast, Flexible Kernels for Quantized Inference

**日期**：vLLM官方博客发布／页面标注更新为 **2026-10-21**。[报告](https://vllm.ai/blog/2026-10-21-humming)｜[代码](https://github.com/vllm-project/humming)｜[检索时可见固定快照db930afa…](https://github.com/vllm-project/humming/tree/db930afa2256cba49b3e46c0589323c3e80b0bfb)。快照页面标注10-22；**它不是作者锁定的benchmark SHA**。代码已有早期历史，本期新增是完整架构与性能报告，不称本周首次实现全部功能。

**机制。** 将数值格式、scale/zero-point与执行pipeline分开：统一量化描述，经padding/repack形成目标layout，再结合Layer/Compute/Tuning Config进行JIT。小M可选cp.async+MMA，大M可选TMA/UMMA；MoE提供Indexed/Grouped调度。Hopper没有原生MXFP4计算时，在内核中将MXFP4权重高效转换到FP8/INT8计算路径，保留4-bit权重存储优势。默认是设备启发式与shape区间dispatch，**autotune仍属未来计划**。

**作者公开端到端实测：8×H20、TP8、DeepSeek-V4.1-Flash，保持MXFP4权重，Marlin W4A16/BF16激活→Humming W4A8/tokenwise FP8激活。**

| 并发 | 后端 | 输入tokens/s | 输出tokens/s | Mean TTFT ms | Mean TPOT ms |
| --- | --- | ---: | ---: | ---: | ---: |
| 1 | Marlin | 2827.15 | 88.30 | 543.13 | 9.24 |
| 1 | Humming | 3226.23 | 100.77 | 383.80 | 8.46 |
| 64 | Marlin | 13937.42 | 442.37 | 5467.35 | 123.25 |
| 64 | Humming | 19973.00 | 633.94 | 3882.94 | 85.70 |

C64输出吞吐 **+43.3%**，Mean TPOT **-30.5%**。输入/输出长度分布、请求率、KV dtype、模型revision、该E2E实验的完整vLLM/Humming/CUDA/PyTorch版本及采样设置未明确；ITL/P99未披露，不从输入输出吞吐比反推长度。图中4.5×等属于特定GEMM微基准，不能代替上述服务收益。

补充工程数据：单W4A16内核编译，在H200服务器、CUDA13.4、编译cache关闭时，CUTLASS+NVCC **23.35s**，Humming+NVCC **1.82s**、NVRTC **1.88s**；这是编译延迟比较，不是请求TTFT。微基准M为1—8192的2次幂，warmup后独立计时、cold L2；MoE比较Gateup+Down总耗时。

**兼容性与复现。** 博客称vLLM0.29.0起CUDA安装含Humming，使用`--linear-backend humming`／`--moe-backend humming`；最低集成版本不等于上述E2E实验精确版本。作者称支持平头哥真武810E，但未给同条件国产平台性能表；仓库README硬件矩阵较博客窄，不能据宣传判定每个格式/设备组合已验证。应锁包版本和镜像，并分别测同激活精度的后端替换、改变激活精度的收益及质量，避免把两者混合归因。

## 3. Elastic Expert Parallelism Scaling in SGLang: Growing a Live MoE Deployment with NIXL

**日期**：官方工程分析 **2026-10-21**。[原文](https://www.lmsys.org/blog/2026-10-21-elastic-ep-scaling-nixl)｜[固定提交测试546965fc…](https://github.com/sgl-project/sglang/blob/546965fc72a73b147323fc839ad0aa955ef64aff/test/manual/ep/test_elastic_scale.py)｜[NIXL dispatcher 77d23a79…](https://github.com/sgl-project/sglang/blob/77d23a796e94c37f8657bc261856db725fa35891/python/sglang/srt/layers/moe/token_dispatcher/nixl.py)。代码可定位，未给统一正式release及完整环境SHA。

**机制。** 在启动时按`max_ep_size`预留元信息和通信buffer，只启动active ranks；外部编排器补充GPU进程后，Mooncake WORLD接纳成员，SGLang在forward边界安装新专家/DP状态，NIXL保留旧连接并扩展peer集合，所有rank同步及图重捕获后才commit并向路由暴露新DP slots。新增GPU仍需初始化，不是API自动分配硬件。

**作者公开实测：**8×H100、DeepSeek-V3-Lite FP8；Elastic从请求扩容到目标拓扑首个canary完成，比restart快 **5.3—8.2×**。端点并不相同：Elastic等待`serving_expanded`并定向新DP rank，restart等`/health_generate`后round-robin。绝对秒数呈于图，本报不估读。扩容准备期间旧组服务，**提交拓扑期间token交付暂停**，不能写成零中断。

图重捕获实验：同平台、256条GSM8K、50 request threads，full-decode graph捕获至batch16的5个shape。

| 迁移 | 扩容后eager平均输出tokens/s | 扩容后full-decode graph |
| --- | ---: | ---: |
| EP4→EP6 | 371 | 1241 |
| EP7→EP8 | 358 | 1120 |

这是graph与eager的 **3.1—3.3×**，不是“弹性扩容相对固定同拓扑”吞吐收益。输入/输出长度分布、请求率、TTFT/TPOT/ITL/P99、详细驱动/CUDA/NIXL版本未集中披露；不能将50线程直接等同于固定50个活跃decode序列。

**版本与限制。** 报告列PR30164、30553、33723、33728已合并，且roadmap按10-04状态描述，故本期新增是10-21系统分析与公开实验，不是实现都在本周合并。full-decode重捕获可用，prefill/piecewise重捕获不支持；scale-down/grow-back、fully-idle progress和扩容后恢复仍有未完成部分。加入WORLD后finalization失败无自动回滚，可能需整组重启。`max_ep_size`越大通信buffer越多，挤占KV容量。公开实验规模为8卡，不能外推多机数百卡稳定性。

## 4. SGLang-TorchTPU: PyTorch-Native Production Serving on TPUs

**日期／版本**：官方报告 **2026-10-20**；[tpu-v0.1.0发布页](https://github.com/sgl-project/sglang-torchtpu/releases/tag/tpu-v0.1.0)页面10-19，commit **00ef120c1e30bf34ef0d48a99f00c5d9ea693f85**，tracking SGLang0.5.22。[原文](https://www.lmsys.org/blog/2026-10-20-sglang-torchtpu/)｜[代码](https://github.com/sgl-project/sglang-torchtpu)；镜像`lmsysorg/sglang:v0.1.0-tpu`，发布页digest `sha256:290b7e1078e64bf5e8de9a83ba5cd02193258b9043fcefc2d6d4564b222805ae`。配套sglang wheel来自该仓库，不能随意换成PyPI同版本包。

**值得关注的工程方法。** 每TPU core一个PyTorch进程，torch.compile降到XLA；prefill按token数、decode按batch数padding至有限buckets，每bucket编译一次，后续按shape复用程序。Pallas paged attention和grouped MoE作为torch.library custom ops接入。它没有采用CUDA式graph capture，不能把编译bucket复用叫作CUDA graph。

TPU Sync在chunked prefill每批提交KV pages后，由D拉取该chunk并与下一chunk计算重叠，只剩末chunk留在收尾路径；D已有前缀pages跳过传输。P/D TP不同，在传输时按KV heads重分片。此处**真实描述了分块产生KV与传输重叠**，与上期NIXL Push仅提前准备接收的机制不同。迁移价值在于shape编译边界、KV page生命周期及重分片验证方法。

**证据强弱。** 硬件验证聚焦TPU v7x：单host4 chips/8 TensorCores、两host TP16、四host 2P+2D；这些是不同配置，不能拼成同一个性能测试。报告没有统一模型/精度/ISL/OSL/并发/QPS下的服务TTFT、TPOT、ITL、P99和tokens/s对照，因此本项不宣称服务加速比。Meta生产使用为机构声明。

作者报告193项TPU测试注册、15模型覆盖；已读取的[固定快照SUPPORT_MATRIX](https://github.com/sgl-project/sglang-torchtpu/blob/515a224f9b0aff92616d76f3aa4159c66b5196be/SUPPORT_MATRIX.md)明确含 **12项disabled**，注册不等于全部通过。该快照SUPPORT.md把Kimi-K3列为4-host Optimized，而生成矩阵只列单host compile等测试，README也称small dummy-weight compile test；不能将其当完整四机准确性/性能证据。应以模型具体测试与日志为准。

RL辅助实验为Qwen3-4B、DAPO-Math-17k、GRPO，4-chip TPU host中2训练/2 rollout，对6×H200、各两seed；曲线在seed波动内，不是同硬件预算的服务性能比较。ICI权重同步“约50×”是计划路径的小测试，未给完整大小/计时，不能当训练E2E提速。

## 5. KVCompass: A Discovery Plane for Internet-Scale Prefix Cache Sharing in LLM Serving

**日期／版本**：arXiv **2610.24179v1**，2026-10-16 19:54:51 UTC，即北京时间 **10-17 03:54:51**。论文另标received10-09，不将received当arXiv公开日。

[原文](https://arxiv.org/abs/2610.24179v1)｜[全文](https://arxiv.org/html/2610.24179v1)｜[在线PDF](https://arxiv.org/pdf/2610.24179v1)｜[代码固定快照dd2bf779…](https://github.com/011shiyiLing/KVCompass/tree/dd2bf779b66dc850fb8db65d978e3bf54a81184e)（页面标10-17）｜[真机复现说明](https://github.com/011shiyiLing/KVCompass/blob/dd2bf779b66dc850fb8db65d978e3bf54a81184e/realmachine/README.md)｜[中文论文笔记](论文笔记/2026-10-23/KVCompass_summary.md)。

**机制。** 多级、无key的Ludo discovery index记录前缀持有者和VRAM/DRAM层级；边缘路由以本地索引联合估计排队、未命中重算、DRAM reload和网络时延，不只追逐最长前缀。远端负载通过响应piggyback和周期broadcast刷新。跨洲主要转发请求到持有者，热门前缀跨区“迁移”采用发送prompt、在空闲目标重算，**不等于跨洲搬完整KV**。

**作者公开真机实测**：三洲14×RTX5090（美8/欧2/亚4），每卡一个SGLang0.5.10 worker，Llama3.1-8B-Instruct BF16；公网单向时延US/EU160ms、US/Asia126ms、EU/Asia149ms。Mixed=50%ToolBench+5%LooGLE+45%APPS，另测WildChat和LMSYS；到达率4—40req/s，延迟分布常取16req/s。真实ISL/OSL分布、并发、KV精度、精确依赖image未完整披露；TPOT/ITL及output/total tokens/s未统一给表，论文“service throughput”不冒充输出token吞吐。

最有迁移价值的消融：同真机Mixed闭环实验，去掉load-aware后服务吞吐 **-34%**，去掉跨区复用 **-10%**，忽略缓存tier **-6%**，去掉主动迁移 **-4%**。该结果说明命中率与端到端性能需要一起优化：hash方案复用10.6M tokens，KVCompass复用9.3M，后者吞吐仍更高。CPU微基准为4096-token prompt、五级表、14-worker打分：转发决策P50/P99 **20.6/21.5μs**，单线程48k decisions/s；不是网络TTFT。

附录另有 **7P+3D RTX5090**、SGLang+Mooncake、24req/s hot-skew Mixed真机：相对各基线median TTFT低1.25—1.69×、P99低1.3—15.7×。所有方案在P同区随机选D，因此此实验隔离的是P路由，不证明D调度或跨区KV传输更快。基线包含stock random、SGLang cache-aware router、RR、consistent hash，倍率是不同基线范围，不是对每种方案的统一收益。

**模拟必须分开。** 64 workers/8 regions及WAN jitter、丢更新的鲁棒性主要是事件模拟。论文承认未在相同设置下量化模拟误差；不能当64卡实测。索引false locator不等于错误复用：worker检查真实cache并重算缺失部分。95%表负载、从未插入key的结构误报45.3%，实际请求false lookup为0.10%／1.27%／0.34%；两组分母不同。索引更新失败无自动重传和确定恢复时间，多模型、跨精度KV兼容性需额外隔离。

## 最值得验证的3个方向

以下是**建议实验，未运行**，4k/1k、16k/1k与64并发不是来源已有统一测试。

### P0：布局感知传输 + 分块流水，先验证正确再测重叠

- **依赖**：本机设备memory registration、DMA/RDMA、完成可见性与KV layout描述；设备backend不具备这些能力时，先做host staging基线。HAWK专用代码未开源，不能计划直接pip复现。
- **最小对照**：相同模型与KV精度，固定1P1D/相同TP，依次测host staging、direct+接收后layout转换、layout-aware transfer；可实现时再对照整请求传输与chunk流水。分别记P侧变换/拷贝、CPU提交、网络传输、D重构与等待。
- **负载**：4k/1k、16k/1k；客户端固定并发1、4、64另行报告max-num-seqs；另外做独立QPS扫描，不能把64并发当64QPS。
- **预期与边界**：目标是降低搬运和转换的串行时间，未必降低decode kernel耗时；小chunk可能被请求/通知开销反噬，受链路带宽约束时收益有限。
- **正确性／稳定性**：逐层KV或首步logits对照、token/block边界和TP重分片；检查未完成页不可见、源/目标块不能过早复用、取消重试后租约回收、bank碎片化与长时OOM。跨主机时间线须同步或用可关联trace。

### P0/P1：量化执行路径与shape分桶联合测，拆开精度变化

- **依赖**：平台支持的低精度指令、编译器、Humming或可比后端、固定量化checkpoint和校准/评测集。
- **最小对照**：先固定激活dtype比较后端；再固定权重将BF16激活改为FP8，单独评估精度影响。MoE测试均衡和偏斜expert token分布，不只测均匀GEMM。编译冷启动、warmup和稳态分别计时。
- **建议**：低并发1/4与64、4k/1k及16k/1k；报告输出tokens/s、TTFT/TPOT和P99 ITL、JIT cache命中/重编译数、padding浪费与显存。动态batch穿过bucket边界，检测编译风暴。
- **预期与检查**：减少反量化/内存流量或编译重复，收益应以端到端确认。检查GEMM误差、溢出/NaN、首步logits、任务准确率、长生成与多轮漂移；框架能加载不代表设备高性能路径已经使用。

### P1：把路由与弹性扩容评测改成“服务连续性 + 容量”

- **依赖**：KV事件/层级观测、可配置router、Mooncake/NIXL或等效通信、拓扑管理与graph重新编译能力。
- **最小对照**：固定资源下比较RR、cache-only、cache+queue+tier；再固定最终拓扑比较restart与elastic。缓存容量一致、同一trace/seed，显式记录max_ep_size预留buffer占用。
- **指标**：TTFT/ITL P99、最长token停顿、扩容请求至新rank首成功输出时间、EPLB收敛、请求失败/重试、KV池实际可用容量和最终稳态输出吞吐。不能只测HTTP健康或cache hit率。
- **稳定性**：加入rank后故障、缺rank、集体通信超时、空闲组进展、图含旧地址/拓扑、扩容后恢复。无自动rollback的路径先在可重启环境验证；异构worker路由须加入设备各自prefill/decode速率，不能照搬同构统一代价。
